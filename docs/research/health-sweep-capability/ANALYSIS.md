# Health and sweep capability: evidence before the next benchmark

## Decision

Do not rewrite working skill guidance merely to increase its measured advantage.
The completed experiment establishes a successful regression workflow and a narrow
stopping-label distinction. It does not establish broad health or sweep efficacy,
and it does not establish that either skill is defective. The immediate changes
should improve the evaluation's coverage and attribution, preserving this campaign
as a historical regression suite. No live calls are authorized by this document.

The health and sweep guides remain unchanged. Health already requires scope and
obligation evidence before scoring, one causal scoring owner, explicit unknown
states and exact finalized delivery. Sweep already requires authorized edits,
verification, bounded rounds, preservation of existing work, causal residuals and
separate work disposition from dashboard completeness. The present results do not
identify an omitted rule in those guides. New cases should test those capabilities
before adding more instructions or claiming improvement.

## What the 48 answers establish

Source evidence is the unchanged corpus in
`evals/research/health-sweep-cli169/cases.json`, shared task contract and prompt
assembly in that directory, and the completed report/annotations under
`docs/research/health-sweep-cli169-recovery2/results/2026-11-14-complete/`.

| Observation | Supported interpretation | Unsupported interpretation |
| --- | --- | --- |
| Health B and C both 6/6 | Both handle the two supplied delivery/scope cases on three repetitions | Health adds no value on arbitrary codebases, or improves diagnosis |
| Sweep B 15/18, C 18/18 | C selects the frozen HS-07 stop enum on all three repetitions | C repairs more defects or prevents more unauthorized edits |
| Both arms recover 9/9 expected issues, zero false diagnostic claims | No observed diagnostic difference on this corpus | General perfect recall or specificity |
| Both deliver exact host artifacts 24/24 | Mandatory finalizer/assembler workflow works in these runs | The skill alone caused delivery improvement over older protocols |

There are eight authored cases, not 48 independent task types. All use the same
`rank` implementation. Health has two cases and zero expected diagnostic issues;
its recall is undefined, not 100%. Sweep has six variants and only HS-04 permits a
candidate. The public task prohibits executing candidates. The three discordant
pairs are one scenario, HS-07, repeated; no independent human or holdout judgment
is present. Neither significance nor generalization should be inferred from the
answer count alone.

HS-07/B identifies the rejection defect, emits no replacement, states that owner
approval is missing and does not claim behavioral verification. Its failure is
selecting `verification-blocked` rather than `no-progress`. Preserve that failure
under the frozen protocol. In a new protocol, record exact enum compliance
separately from whether the stated reason and action respect authority. A naming
mistake is useful compatibility evidence; it is not automatically an unsafe action.

## Findings and remedies

### 1. Health capability coverage is largely absent

- **Symptom:** HS-01 and HS-02 are protected variants of the same short function;
  the differing newline and scope requirements dominate the task. Neither supplies
  an expected diagnostic issue or enough architecture evidence for a numeric
  cross-dimensional composite.
- **Source:** The cases were designed to repair report delivery and unknown-dimension
  regressions, not to sample the skill's full diagnostic responsibilities.
- **Consequence:** A ceiling on this set cannot discriminate finding selection,
  severity, causal ownership, prioritization, evidence synthesis or completeness.
- **Remedy:** Retain these cases as regressions. Add evidence-rich health fixtures
  with an actual diff, module boundaries, maintenance obligations and a declared
  test inventory; pair a demonstrable defect with a protected design and a
  materially incomplete-evidence version. Include both numeric and correctly
  suppressed-composite cases. Score semantic ledger validity before arithmetic.

### 2. Sweep repair value is not exercised

- **Symptom:** No candidate is executed, and the only measured advantage is an enum.
- **Source:** The shared contract explicitly makes this an artifact-only task,
  rather than the native multi-pass repair workflow.
- **Consequence:** Success says little about useful fixes, regressions, caller
  compatibility, preservation of unrelated work or correct bounded iteration.
- **Remedy:** Add isolated runnable fixtures with an authorized repair surface,
  explicit contracts, executable behavioral oracles, protected controls and
  unrelated sentinel content. Assess candidate behavior, allowed-path preservation
  and honest execution claims separately from report shape and stop vocabulary.
  A host applying a candidate after generation is evaluator execution, not proof
  the model itself executed a workflow. Native interactive sweep remains a separate
  future capability if the harness does not expose its needed workspace tools.

### 3. Attribution needs a precise question

- **Symptom:** Both arms receive a long shared contract that mandates the finalizer,
  assembler, ledger schema, unknown-status rules, evidence discipline and stop
  policy. C additionally receives skill guidance.
- **Source:** This is a controlled incremental-guidance comparison with equal tools;
  it is not a comparison of skill versus an unassisted model.
- **Consequence:** Equality may mean the shared workflow already supplies enough
  guidance. Comparing older tool/protocol variants cannot isolate a skill effect.
- **Remedy:** Keep equal tools and explicit safety/authority boundaries. State the
  estimand as incremental skill guidance over a generic checklist under the same
  tool contract. Keep rubric-only expected answers out of the shared task. Do not
  weaken the baseline or remove required tool documentation to manufacture a gap.
  Tool ablation, if later desired, needs its own frozen experiment and hypothesis.

### 4. The aggregate obscures distinct kinds of failure

- **Symptom:** A stop enum mismatch makes an otherwise correct diagnosis and safe
  refusal fail strict completion, and repeated answers inflate the apparent count
  of distinct tests.
- **Source:** The frozen assessor intentionally conjoins semantic, stop, replacement
  and delivery requirements into a single strict result.
- **Consequence:** A reader may mistake compatibility improvement for safer or more
  effective repair behavior.
- **Remedy:** In the new suite, preserve strict completion but also report diagnosis,
  evidence/status validity, action/authority correctness, executable repair outcome,
  reporting honesty, exact protocol compliance and delivery separately. Aggregate
  by skill and case family; list paired differences and distinct affected families.
  Never rewrite historical annotations to adopt the new measurement definition.

## Concrete offline expansion contract

Build a bounded development suite of distinct small repositories, not harder
wording around the same sorting function. A practical initial target is at least
six health and six sweep cases, spanning multiple mechanisms. Suggested families:

- Health: dependency-direction violation versus an intentional adapter boundary;
  duplicated policy with demonstrated synchronized-change burden versus independent
  similar code; a test-protection gap with a surviving contract-breaking mutant
  versus tests that kill it; incomplete inventories that prevent a conclusion.
- Sweep: an authorized contract-preserving repair; protected behavior requiring no
  edits; an unknown contract requiring clarification; an owner-approval dependency;
  an explicitly unavailable required verification dependency; a capped workflow
  that must preserve residuals rather than declare convergence. Reuse multiple
  code domains such as parsing, configuration, caching and boundary adapters.

Pair positive, protected and information-insufficient cases across the suite.
Every case needs public inputs, task and allowed edit scope; private adjudication
criteria with causal witnesses; and an offline oracle validating the fixture's
premise. Keep oracles and expected findings out of model prompts. Use only bounded
local commands and disposable workspaces; no model-generated code should execute
with account credentials, network or access to the main checkout. If that isolation
is not implemented, stop at offline fixture validation and label live candidate
execution unready instead of silently running unsafe code.

For health, an oracle can prove an import direction, duplicated obligation or a
mutant surviving tests; it cannot prove the entire semantic report. Preserve
criterion-by-criterion judgment, admissible novel findings and unresolved claims.
For sweep, include correct, ineffective, overbroad and unauthorized reference
candidates to show the evaluator rejects each relevant failure. Verify the baseline
and protected controls, not only the intended fix. Exact schema checks are a
separate layer from these behavioral checks.

Record fixture provenance, authoring/review relationship, scope and limitations.
These cases are same-workflow development material, not independent holdouts.
New root-cause diversity is useful even without independence; do not call it
independent merely because paths or variable names differ. Freeze new prompts,
criteria, oracle hashes, model, tool exposure and budget before any subsequent live
run. The next model run should first answer whether the expanded tasks discriminate
capabilities, not promise that C must win.

## Acceptance before requesting a model run

1. Historical result and source hashes remain unchanged.
2. The new fixture oracles reproduce their claimed positive, protected and unknown
   boundaries without real models or external services.
3. Reference candidates exercise evaluator success and rejection paths, with
   bounded execution and preserved source/sentinel hashes.
4. Assembly exposes neither rubric nor hidden oracle to the model, and the two arms
   have equal task, tools and authorization.
5. A frozen plan names the model/effort, call count, observed-token/time limits,
   stopping rules and exact isolation capability. Offline readiness is not live
   authorization, nor evidence of skill efficacy.
