# 从费马大定理的形式化到 brooks-lint 的 CI 可靠性

调研日期为 2026-11-26，代码基线为 `5e2d4b9`。本文供项目维护者决定是否投入试点。

**建议先花 3 人日，验证一条用户可见的承诺：只有完成审查且满足所选门禁策略的报告，才能被下游解释为“审查通过”。** 空 diff 也是一次正常结束，但没有质量结论。这个区别横跨 Git 输入、模型报告、解析器、命令退出码和 GitHub Action 输出。只验证一个算分函数，会漏掉最值得验证的部分。第一阶段可以完全离线进行。

## 两份费马项目资料分别回答什么问题

费马大定理断言，对任何正整数 a、b、c 和整数 n ≥ 3，都有 aⁿ + bⁿ ≠ cⁿ。这里连“正整数”都属于规格：若误写成允许 a = 0，则 b = c 就是反例。软件里的同类错误是把“进程正常退出”写成“审查通过”。检查器越强，越需要先确定送进去的命题表达了用户关心的事。

| 一手材料 | 可观察的做法 | 在本项目中的对应动作 |
|---|---|---|
| Imperial 的公开蓝图 | 把最终结论分解成有依赖关系的子目标，公布阶段内暂时假设成立的既有数学结果；各小项目能独立推进。[项目蓝图](https://imperialcollegelondon.github.io/FLT/blueprint/sect0001.html) | 画出从 diff 到下游结论的依赖关系，把“输入由本次 runner 产生”等假设写在依赖边上。 |
| Anthropic 发布的 Lean 成果 | 默认构建检查最终定理依赖的公理；用独立给出的 Mathlib 命题作比较，并报告用第二个内核重放。Kevin Buzzard 说明该成果使用的证明路线和 Imperial 正在整理的路线有所不同。[成果与复核入口](https://github.com/anthropics/fermats-last-theorem) · [Buzzard 的说明](https://xenaproject.wordpress.com/2026/09/04/flt-anthropic-has-beaten-me-to-it/) | 先由维护者按公开契约写参考判定表，冻结后再比较生产代码。比较时让参考模型和实现分别读取同一原始样例，防止两者共享一个错误的预处理结果。 |
| Lean 对公理的说明 | 未完成的证明可以通过占位符引入假设；最终结论依赖哪些公理是可检查的信息。[Lean 参考手册](https://lean-lang.org/doc/reference/latest/Axioms/) | 在验收记录中区分已证明的模型性质、已运行的实现样例和依赖外部系统的假设。复跑时同时固定规格、代码、夹具和工具版本。 |

上述数学成果的验证结果来自作者公开记录。本调研实际运行的对象是 brooks-lint。软件中还有文件、服务和操作者，最终能够声明的保证要写清楚输入范围、版本和消费结果的方式。

### 软件工程里怎样选择验证方法

AWS 工程师在 2015 年发表的实践报告中，用 TLA+ 描述分布式算法并检查并发事件次序。对 brooks-lint，值得借鉴的是选择抽象层级：发布重试的先后顺序适合画状态机；严重度策略这样的小型确定性接口，直接枚举输入就能得到廉价且可复跑的证据。给发布流程建模时，应保留“同一 SHA 有多次运行”的身份关系，省略网络响应耗时等与放行条件无关的细节。若模型找到反例，先把那条事件序列重放到真实发布检查，再判断是否需要调整实现。[AWS 工程团队的原始论文](https://www.amazon.science/publications/how-amazon-web-services-uses-formal-methods)

## 现状与证据

1. **输入。** Git 收集失败会使 review runner 报错。成功收集到空 diff 时，runner 返回 skipped、空报告和 null 分数，并在请求模型之前退出。这两条路径需要不同的结果。[runner 契约](../runner-contracts.md) · [生产入口](../../scripts/ci-review.mjs)
2. **解析。** 解析器识别报告范围、分数和活动发现，并处理示例与被抑制内容。此次复跑冻结语料，30/30 份报告的严重度计数与标注完全匹配，风险码 TP=56、FP=0、FN=0，30/30 通过仓库的 SARIF 检查。这个分母是已收藏的报告；新增 Markdown 变体仍需要新的证据。[基准程序](../../scripts/benchmark.mjs) · [现有契约测试](../../scripts/report-contract.test.mjs)
3. **判定与消费。** CLI 的 skipped 和合规报告都能退出 0。Action 另行导出 skipped 与 score，按 skipped 控制门禁与 SARIF 上传。直接调用 CLI 的消费者如果只记录退出码，会丢掉这一区别。它是接口信息损失的例子；本次未观察到线上误放行。[门禁入口](../../scripts/ci-gate.mjs) · [Action 输出与条件](../../.github/actions/brooks-lint/action.yml)
4. **诊断真实性。** 判断一个文件是否真的发生 R2 变更传播，还需要调用方、变更原因和反例。已有 health 行为研究中，基线通过 15/18，使用技能通过 10/18；该研究记录了过度弃判。即使账本和分数完全一致，也不能据此推断诊断能力提高。[项目行为证据及样本限制](../benchmark-evidence.md)

### 已执行的小实验

从工作树根目录运行下面的 Node 程序。参考答案取自策略允许阻断的严重度集合；生产函数采用计数和阈值。每种严重度取 0、1、2，交叉三种策略，共 81 个输入，实测差异为 0。多次出现同一严重度与混合严重度均在该范围内。实验直接调用生产函数，尚未经过 Markdown、CLI 或 Action。

```sh
node --input-type=module <<'JS'
import { severityBreached } from './scripts/ci-gate.mjs';
const blocked = { none: [], warning: ['warning', 'critical'], critical: ['critical'] };
let checked = 0;
for (const critical of [0, 1, 2]) {
  for (const warning of [0, 1, 2]) {
    for (const suggestion of [0, 1, 2]) {
      const counts = { critical, warning, suggestion };
      for (const [policy, levels] of Object.entries(blocked)) {
        const expected = levels.some(level => counts[level] > 0);
        if (severityBreached(counts, policy) !== expected) {
          throw new Error(JSON.stringify({ counts, policy, expected }));
        }
        checked++;
      }
    }
  }
}
console.log(checked);
JS
```

另用四份手工 JSON 封装直接运行 `node scripts/ci-gate.mjs --report <file> --fail-on warning`，观察退出码和消息。完整样例含 review 模式、范围、100 分和无发现正文。截断及分数不符样例各只改一个字段。

| 输入 | 实测退出码 | 实测含义 |
|---|---:|---|
| skipped、空正文、null 分数 | 0 | 明示无分数、无质量结论 |
| complete、有效正文、封装分数 100 | 0 | 质量门禁通过 |
| 同一完整样例加 truncated=true | 1 | 报告完整性检查失败 |
| 同一完整样例的封装分数改为 90 | 1 | 封装与正文分数不一致 |

这四次重放验证了门禁消费 JSON 时的行为。上游如何取得 diff、GitHub 托管环境怎样解释输出，仍是独立的验证环节。

## 首个试点如何设计

**研究问题。** 对由本次 runner 产生的输入，开启指定门禁后，是否存在“没有有效审查却获得质量结论”，或“应被阻断却放行”的执行路径？优先调查假通过，同时记录误阻断。下表是拟冻结的独立判定表。Passed 表示已启用的策略通过，Blocked 表示有效报告触发策略，Invalid 表示流程或证据失败，Skipped 表示正常无结论。

| 原始事实 | 期望语义结果 | 检查哪个观察量 |
|---|---|---|
| Git 读取失败 / 引用不可用 | Invalid | runner 非零退出，不产生可消费的分数 |
| 成功读取空 diff | Skipped | 无模型调用，score 为空，Action 跳过阈值和上传 |
| 非空 diff，报告截断、解析失败或封装分数与正文不符 | Invalid | 在各自入口拒绝，消费者不能发布通过结论 |
| 完整报告，活动 critical ≥ 1，fail-on=warning | Blocked | 从正文重算计数，门禁失败 |
| 完整报告，唯一 warning 位于合法 suppression 块中，分数 100，策略为 warning | Passed | 活动计数为零，该项不进入 SARIF |
| 完整报告，分数恰好等于最低分，其他门禁均满足 | Passed | 通过包含等号的边界；将分数减一应触发阻断 |
| 开启回归门禁，历史存在且 delta < 0 / 历史缺失 | Blocked / 仅停用回归项 | 历史缺失时仍检查严重度和最低分 |

**拟验证的性质。** 在合法计数域内，固定其余输入，增加一个活动 critical 不能让已触发的严重度门禁恢复通过。对空 diff，任何严重度策略都不产生质量结论。对非空 diff，Passed 必须蕴含报告完整、分数有效且每一项已启用策略均满足。每个蕴含式都加一个真正能 Passed 的样例，防止“拒绝一切”的实现也通过验收。

**假设与兼容。** CLI 当前接受省略 status 的部分旧封装，而 Action 取分步骤要求显式 complete 或 skipped。分别为两个入口制定期望，先测兼容行为。把 runner 产生的正规封装与手工构造的矛盾封装分开计数，例如 skipped 同时携带数值分数。后者用于调查谁拥有校验责任；若要收紧历史输入，需要单独作兼容性决定。GitHub 环境、模型诊断真伪和任意 JavaScript 程序的语义都超出这组命题。

### 工作包、成本和退出条件

以下是单维护者的排期估算。实际时间按规格讨论、夹具构造、排错和复核分别登记。

| 时间 | 工作与交付物 | 验收或停止条件 |
|---|---|---|
| 第 1 天 | 从 runner 契约独立写判定表。对每个状态列出输入来源、预期分数、退出码、上传资格。为 skipped、旧格式和无历史各写一个正例和近邻反例。 | 维护者能在不读生产函数的情况下给每个样例判定结果。有争议的格子标为待决，不进入准确率分母。 |
| 第 2 天 | 用临时 Git 仓库重放无效引用及空 diff。其余样例用冻结响应离线驱动 parser、CLI 和 Action 的本地可执行步骤；保留实际输出、退出码及最小失败样例。 | 分别报告状态覆盖、预期/实际差异和本地不能复现的托管步骤。独立复跑获得相同结果。 |
| 第 3 天 | 在临时副本逐项注入四种错误：忽略截断、把空 diff 标成完成、把严重度条件反转、把最低分比较改成排除等号。记录现有测试与新增检查分别发现了哪些错误。 | 原实现每个约定格子都通过或有可复现差异，每个变异至少被相应期望捕获一次。若现有测试已全部捕获且没有新增契约歧义，交付判定表并停止追加工具。 |
| 可选追加 2–3 天 | 仅在仍有难以穷举的组合性质时，固定 Lean 版本，以归纳类型描述状态，用自然数描述计数，证明严重度单调性及 Passed 的必要条件。让模型导出测试向量，对真实 CLI 做差分。 | 公理依赖可审计、无占位证明、从干净环境可重放，并报告模型与 JS 的差异。若主要成本落在 Markdown/GitHub 适配，保留可执行规格和反例，停止扩大 Lean 范围。 |

试点成功的证据应是一个此前未覆盖的反例、一项被澄清的用户契约，或能够覆盖无界输入且可维护的模型定理。报告同时公布原有检查已捕获的变异数、新增捕获数、剩余数和新增运行时间。四个变异来自设计者，只能比较这四类故障。即使 Lean 模型全绿，也要单列模型到 JavaScript、JavaScript 到 Action、Action 到调用工作流三处连接的验证方式。

## 何时扩展到其他能力

| 候选 | 潜在保证与方法 | 排序理由 |
|---|---|---|
| Health/Sweep 账本 | 对同一组已评估维度，重放扣分、下界和合成分；生成“缺少必要维度”“无 diff 只跳过 PR 维度”等相邻样例，与现有 finalizer 差分。[账本实现](../../skills/brooks-health/scripts/score-dashboard.mjs) | 第二顺位。算术容易形式化，最值得确认的是缺少证据时是否仍显示数字。 |

| R/T 诊断效果 | 用带调用链的真实改动和干净对照样例，由复核者核对证据是否支撑风险码、后果和修复；另报漏检、误报与分歧。[已有评估口径](../benchmark-evidence.md) | 保持独立的行为评估。证据位置存在可机械检查，证据足以支持结论需要领域判断。 |
