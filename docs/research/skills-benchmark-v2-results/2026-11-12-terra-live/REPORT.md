# All-skills v3: 108-response adjudication

The campaign provides **no evidence of a general diagnostic-recall improvement from the skill treatment**: every arm finds all 11 frozen expected issues. The supplied skills improve some workflow and reporting behavior, particularly bounded sweep decisions and source-ledger taxonomy, but do not consistently improve evidence completeness. Several apparent failures expose benchmark underspecification rather than a demonstrated skill defect. Frozen-label agreement must not be presented as complete answer correctness.

## Metric definitions and judgment rules

**Frozen-label agreement** is the number of answers whose scoped disposition matches the original defect/protected/unresolved label. It does not require complete evidence, a usable artifact, sound scoring, or a correct tool receipt. A valid novel defect can disagree with an incomplete frozen label without being a false positive. The original labels were not changed after viewing results.

**Missed expected issues** counts frozen expected issue IDs not substantively diagnosed. Names and variable spelling need not match; incorrect optional risk-code assignments are separately recorded. Some unresolved cases contain a demonstrated local issue, so the denominator is issue IDs, not simply defect-labeled cases. **Confirmed false-defect claims** count unjustified diagnoses; **other unsupported claims** include execution provenance, score arithmetic, taxonomy and configuration errors. **Pending claims** preserve disputed additional findings and are excluded from confirmed false positives. These are claim counts, not a conventional binary false-positive rate.

Evidence credit requires the actual content requested by each frozen item. A concrete callable expression with inputs and expected outcomes, executable snippet, or a precise reference to supplied executable assertions can earn witness credit. A prose mechanism or list of test categories alone cannot. Generic rename consequences can establish behavior-preserving-rename reasoning; paired original/renamed-check credit additionally requires a concrete renamed form and both check outcomes. A passing arithmetic receipt cannot establish ledger truth.

Scoped local warnings in unresolved pipeline cases do not become claims of proven production leakage when the answer explicitly retains unknown cache ownership/build/identity facts. BV2-06 differs because even architectural ownership and the rule prohibiting direct import are absent; its retained scored warning is adjudicated strictly below, with sensitivity disclosed. For bounded workflow criteria, a syntactically usable artifact and truthful verification record matter in addition to diagnosis. Source-derived dashboard credit also requires supported ledger construction and preservation of the finalizer output. These are operational interpretations of terse frozen criteria, not independent ground truth; the item-level records make them reviewable.

## Adjudication-sensitive and benchmark defects

1. **Valid new numeric findings, BV2-02 and BV2-03.** For the safe integer `9007199254740901`, `Math.round(x * 5000 / 10000)` yields `4503599627370450`, while exact half-up integer arithmetic gives `4503599627370451`. Also `Number.isInteger(1e308)` is true: the multiplication overflows, although `1e308 / 2` is finite. BV2-02 A/C and BV2-03 A accurately identify these. Preserve their frozen-label mismatches, but do not call them false positives. A purely illustrative sensitivity accepting these novel defects changes agreement to A 35/36, B 34/36, C 33/36; it is not a replacement score.
2. **Disputed adequacy, BV2-11.** All arms exhibit or describe a hardcoded function that passes two examples. Mutation survival is real, but no independent business specification establishes that more arbitrary interior examples are an actionable requirement. Each arm has one pending claim. The frozen protected label is not a complete specification of test adequacy.
3. **Disputed maintenance finding, BV2-26.** All arms discuss duplicated lookup/population work beyond the protected shared key implementation. Whether this warrants an actionable finding needs an explicit ownership/change-cost rule. B/C retain scored findings and differ from the frozen protected label; A's optional concern leaves its disposition protected. Each arm has one pending claim. Do not automatically count all six pending claims as FP.
4. **Conditional scored finding, BV2-06 C.** The answer concedes that ownership and active binding are unknown, but retains an R5 Warning and score deduction. Strict adjudication treats the deduction as unjustified. Reading the conditional prose as the controlling verdict would instead classify this answer unresolved, move its claim to pending, and yield C 33/36 with zero confirmed FP. This single case does not support a robust claim that C has a higher false-positive rate.
5. **Missing challenge artifact contract.** BV2-34–36 reference the regression sweep artifact schema without including its exact phase strings, stopReason enumeration, or total-round rule. All nine challenge answers use non-enumerated stopReason; eight use phase objects; one reports zero rounds. A BV2-35 answer explicitly notices the missing schema. Frozen exact criteria remain failed, but this is a benchmark delivery defect. Conditional returned patches for the unknown-contract variant remain a separate decision-boundary concern.
6. **Taxonomy/configuration asymmetry.** The public protocol exposes allowed risk codes and presets, but does not explain their meanings or the default preset. C receives that information through skill text; A/B do not. Many A/B source-derived ledgers choose arbitrary R1/T1 labels or strictness. These are unsupported relative to the repository semantics, but the reduction in such claims in C cannot be generalized to reduced hallucination or superior independent reasoning. The next benchmark should supply a common output vocabulary/default to every arm, while keeping diagnostic guidance as the treatment.
7. **Unknown dimensions and arithmetic.** BV2-36 C returns an exact scorer report with a numeric composite despite incomplete architecture/test evidence. A valid receipt proves arithmetic only. Several other answers claim running JavaScript witnesses without execution events; all item/completed event types were checked and none contains an execution tool event. These provenance errors are separate from whether the illustrated calculation is correct.

## What the results establish and what to do next

There is a limited positive signal for C in workflow discipline, risk vocabulary and sweep evidence, with no demonstrated gain in frozen issue recall and no consistent evidence-completeness advantage over the generic checklist. The data do not justify labeling all skills effective or ineffective, or claiming statistical significance from six correlated cases per skill.

Before another live round, correct benchmark delivery: include the complete action/output contract in each challenge prompt; publish a neutral risk vocabulary/default scoring policy to every arm; specify how novel valid findings and test-adequacy objections are adjudicated; add independent contract-complete holdouts and actual sandboxed artifact checks. Keep this frozen campaign unchanged and distinguish revised-case development from independent validation. Skill work suggested by these answers is narrower: preserve concrete executable witnesses, avoid scored conclusions when the governing architectural rule is unknown, carry finalizer output byte-for-byte, and prevent complete dashboard scores from incomplete evidence.
