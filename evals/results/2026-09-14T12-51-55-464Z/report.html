## Bug: `run-evals-live.mjs` never authenticates to ExampleGW

In `ci-review.mjs`, the `examplegw` credential flow works because **`action.yml`** does the heavy lifting first:

```bash
export ANTHROPIC_API_KEY="$EXAMPLEGW_API_KEY"
```

before invoking the script — so by the time `new Anthropic({ baseURL: ... })` runs, `ANTHROPIC_API_KEY` is already the gateway key.

`run-evals-live.mjs` has no such wrapper. It's invoked directly (per its own updated header comment: `EXAMPLEGW_API_KEY=... node scripts/run-evals-live.mjs --provider examplegw`), but the script:

- never reads `process.env.EXAMPLEGW_API_KEY`
- never passes `apiKey` to the `Anthropic` constructor
- only sets `baseURL` when `provider === "examplegw"`

The Anthropic SDK's credential resolution falls through `ANTHROPIC_API_KEY` → `ANTHROPIC_AUTH_TOKEN` → active OAuth profile → WIF → default profile-on-disk if the key isn't explicitly passed. So on a machine with a local `ant auth login` profile or `ANTHROPIC_API_KEY` already exported for other work, this script will silently authenticate with **real Anthropic credentials against ExampleGW's `baseURL`** — sending Anthropic secrets to a third-party host — rather than failing loudly or using the gateway key. That's a credential-leakage risk, not just a broken feature.

Fix: in both scripts, when `provider === "examplegw"`, explicitly construct the client with the gateway key rather than relying on ambient env state:

```js
new Anthropic(
  provider === "examplegw"
    ? { baseURL: EXAMPLEGW_BASE_URL, apiKey: process.env.EXAMPLEGW_API_KEY }
    : undefined
)
```

This also removes `ci-review.mjs`'s implicit dependency on the bash wrapper — right now that script silently does the wrong thing if anyone runs it directly (e.g. local testing) without replicating the `action.yml` export line.

## Verified as correct

- **`baseURL` constructor option** — correct key for the TS/JS SDK (confirmed against the SDK reference; Python's equivalent is `base_url`).
- **`thinking: { type: "disabled" }`** — this is a real, valid shape, and it's accepted for Sonnet 5 (which `anthropic/claude-sonnet-5` presumably resolves to on the gateway). No hallucinated parameter here.

## Worth a second look, not blocking

- **`"anthropic/claude-sonnet-5"` model ID format** — Anthropic's own model IDs are never provider-prefixed like this; that's an OpenRouter/aggregator-style convention. It's plausible this is exactly how ExampleGW namespaces models internally, but it's worth explicitly confirming against ExampleGW's model catalog before merge — a wrong/stale ID here only surfaces as a runtime error, not a type error.
- **Disabling thinking outright vs. lowering effort** — general guidance for Sonnet-5/Opus-5-tier models is to prefer `output_config.effort: "low"|"medium"` over fully disabling thinking, partly because disabled thinking can occasionally leak stray `<thinking>`-tag text into the visible response. These scripts don't declare `tools`, so the "tool call written as text" failure mode doesn't apply, but if the leaked-tags issue shows up it would land inside the JSON/SARIF-bound output these scripts parse. Might be worth a quick eval run against `run-evals-live.mjs --provider examplegw` to confirm output stays clean before relying on it in CI.
- **Default model for `provider=anthropic`** stays `claude-sonnet-4-6` (previous-gen) — unrelated to this PR's purpose, so not a blocker, just flagging in case you want to align defaults while you're in this code.

import { randomUUID } from "node:crypto";
import type { Clock, Order, OrderRepository, PaymentGateway } from "./ports";

export class PlaceOrder {
  constructor(
    private readonly orders: OrderRepository,
    private readonly payments: PaymentGateway,
    private readonly clock: Clock,
  ) {}

  async execute(customerId: string, amountCents: number, currency: string): Promise<Order> {
    if (!Number.isInteger(amountCents) || amountCents <= 0) {
      throw new RangeError("amountCents must be a positive integer");
    }

    const order: Order = {
      id: randomUUID(),
      customerId,
      amountCents,
      currency,
      status: "pending",
      createdAt: this.clock.now(),

    // reconciliation job can retry (the idempotency key is the order id).

    await this.orders.save(settled);

The difference is what type each expression is checked *against* and what type it ends up *with*.

**`satisfies`**

```ts
const routes = {
  home: { path: "/", auth: false },
  settings: { path: "/settings", auth: true },
} satisfies Record<string, Route>;
```

`satisfies` checks that the literal you wrote is assignable to `Record<string, Route>`, but then keeps the *original, narrower inferred type* for `routes` — not `Record<string, Route>`. Each property of the object literal still has to individually be a valid `Route`, so `settings` must have both `path` and `auth`. Delete `auth`, and `{ path: "/settings" }` is no longer assignable to `Route` (missing required property), so it fails at the site of the literal. That's the whole point of `satisfies`: full structural checking of the literal, while preserving literal types (e.g. `routes.home.path` is `"/"`, not just `string`).

**`as`**

```ts
settings: { path: "/settings" } as Route,
```

`as` is a type assertion — you're telling the compiler "trust me, treat this as a `Route`," and TypeScript only does a compatibility sanity check (do the types overlap enough that this isn't obviously nonsense), not a full structural check. Since `{ path: "/settings" }` and `Route` overlap (they share `path`), the assertion is allowed even though the object is actually missing `auth`. It compiles, but you've just lied to the compiler — at runtime `legacyRoutes.settings.auth` is `undefined`, not `boolean`, and nothing will catch that.

**Bottom line:** `satisfies` validates structurally and infers precisely; `as` overrides the checker and can hide missing/wrong fields exactly like this.
