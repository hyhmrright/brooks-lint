## Technical verification

**1. `new Anthropic({ baseURL: "..." })` for a third-party gateway — fine.**
The "use the platform's dedicated client, not `baseURL`" rule only applies to the three Anthropic-partnered hyperscaler platforms (Bedrock/Foundry/Vertex), which have dedicated SDK classes. For a generic third-party "Anthropic-compatible" gateway there's no dedicated client — `baseURL` (equivalently `ANTHROPIC_BASE_URL`) is the documented, supported mechanism. The comment about the SDK appending `/v1/messages` to the base URL is also accurate.

**2. `thinking: { type: "disabled" }` — works, but is the wrong fix.**
For the model actually in use here (`anthropic/claude-sonnet-5` via the gateway), `disabled` is a legal value — it won't 400. But the documented pitfall (real, not model-specific in practice) is that disabling thinking entirely can cause the model to write a tool call into visible text instead of leaking `<thinking>` tags into the output — silently corrupting the review output text/JSON this script parses. Since the actual complaint here is "reasoning eats the 4096-token budget," the correct fix is `output_config: { effort: "low" }` (or `"medium"`) with thinking left on `adaptive`, not `disabled`. That gets the token-budget control they want without the leakage risk. Worth raising as a should-fix, not a blocker.

**3. Model ID defaults — real IDs, but inconsistent across providers.**
`claude-sonnet-4-6` and `claude-opus-4-6` are real (previous-gen) IDs, not fabricated. The actual issue: the PR makes the `anthropic` path default to `claude-sonnet-4-6` (older gen) while the `examplegw` path defaults to `anthropic/claude-sonnet-5` (current gen). Same CI review action, two different model generations depending on which provider flag is set — that's a silent quality/behavior divergence a reviewer running `provider=anthropic` vs `provider=examplegw` wouldn't expect. Pre-existing default aside, this PR is a natural point to also bump the anthropic-path default to `claude-sonnet-5`.

**4 & 5. Reusing `ANTHROPIC_API_KEY` for the gateway key — mechanically works, but rests on an unverified assumption.**
The SDK's zero-arg client reads `ANTHROPIC_API_KEY` and sends it via the `x-api-key` header (not `Authorization: Bearer`). So `export ANTHROPIC_API_KEY="$EXAMPLEGW_API_KEY"` will work correctly **only if ExampleGW also authenticates via `x-api-key`**. If ExampleGW instead expects `Authorization: Bearer sk-gw-...` (common for many gateways), every request will 401 and the failure mode is opaque (the action would just fail on the API call, not at the validation step). This should be confirmed against ExampleGW's actual docs before merging, and ideally exercised once in CI against a real (or sandboxed) gateway endpoint rather than assumed from the "Anthropic-compatible" label. The `export` is correctly scoped to that one `run:` step (not written to `$GITHUB_ENV`), so there's no cross-step leakage — that part is sound. No beta headers are used (plain `client.messages.create`), so there's nothing beta-specific for the gateway to replicate.

## Fix before merging

**Disabling thinking outright is the wrong lever, and it's not free.** On Sonnet 5 (and Opus-5-tier models generally), `thinking: {type: "disabled"}` is accepted, but with a known failure mode: the model can occasionally write a tool call into its **visible text** instead of a proper block, or leak reasoning-tag artifacts into the output — with no error raised. `ci-review.mjs` takes `message.content[0]?.text` and feeds it straight into the report/SARIF pipeline, so any leaked tags would silently corrupt the CI output rather than fail loudly.

The token-budget problem this is solving (thinking eating into a fixed `max_tokens: 4096`) is better solved with `output_config: { effort: "low" }` (or `"medium"`) — this keeps adaptive thinking on (avoiding the leak mode) while still capping how much of the budget goes to reasoning. Sonnet 5 supports `effort` natively. I'd swap the `thinking: {disabled}` block for this in both `ci-review.mjs` and `run-evals-live.mjs`.

## Worth verifying

- **`anthropic/claude-sonnet-5`-style model ID**: provider-prefixed model strings aren't an Anthropic API convention — they're purely a gateway's own routing syntax. Since you've anonymized the real value, I can't check it, but confirm it's copied verbatim from ExampleGW's current docs, not inferred from the bare Anthropic ID by pattern-matching. Gateways change these prefixes without much notice.
- **Default-model remap is duplicated and fragile.** `ci-review.mjs` computes `DEFAULT_MODELS[provider]` when `--model` is *absent*, but `action.yml` always passes `--model "$MODEL"` (from the input's own default), so that mjs fallback is dead code on the action path — only the shell's `if [ "$MODEL" = "claude-sonnet-4-6" ]` string match actually does the remapping. If the action's `model` input default ever changes, this silently stops firing and the raw Anthropic model ID gets sent to ExampleGW. Simpler fix: default the `model` input to `""` in `action.yml` and let `ci-review.mjs`'s existing `args.model ?? DEFAULT_MODELS[provider]` be the single source of truth.

## Looks right

- Using the bare `Anthropic` client with a `baseURL` override for a third-party gateway is the correct pattern (dedicated provider clients like `AnthropicBedrockMantle`/`AnthropicVertex` only exist for Anthropic's own platform partners — ExampleGW isn't one, so `baseURL` is the intended mechanism here).
- `EXAMPLEGW_API_KEY` → `ANTHROPIC_API_KEY` handoff and the required-unless-examplegw validation in `action.yml` are sound; the native Anthropic path is unaffected by the new branch.

Yes — the boundary condition and the arithmetic type don't match between the two modules, and that's a real bug for orders that land at or near $100.

**1. Free-shipping threshold is inconsistent (off-by-boundary)**

`pricing.py` grants free shipping when `subtotal >= FREE_SHIPPING_MIN` (i.e. **>= $100.00**).

`cart_banner.py`'s `shipping_banner` checks `total > 100` (**strictly greater than**).

So for an order that totals exactly $100.00:
- `pricing.quote()` → `shipping = 0.00` (free)
- `cart_banner.shipping_banner()` → falls to the `else` branch and prints `"Add $0.00 more to get free shipping"` instead of the congratulations message.

Customer sees a message telling them to spend more while checkout has already given them free shipping.

**2. `cart_banner.py` recomputes the subtotal independently, using `float` instead of `Decimal`**

`cart_total` does `float(i.unit_price) * i.quantity` and sums with plain floats, then `shipping_banner` rounds with Python's built-in `round()` (banker's/round-half-to-even). `pricing.py` does everything in `Decimal` and rounds with `ROUND_HALF_UP`.

Two problems from this:
- Float conversion of `Decimal` prices can introduce tiny binary-floating-point error (e.g. a cart that's exactly `100.00` in Decimal can come out as `99.99999999999999` or `100.00000000000001` as a float sum), which can flip the free-shipping check right at the threshold — compounding bug #1.
- Even when it doesn't flip, `round()` vs `ROUND_HALF_UP` can disagree on `.xx5` cases, so the banner's displayed "remaining amount" can differ by a cent from what checkout actually charges.

**Fix**: don't reimplement the subtotal logic in `cart_banner.py` at all — import and call `quote()` from `pricing.py` and reuse its `Decimal` subtotal, comparing against `FREE_SHIPPING_MIN` with `>=`:

```python
from pricing import LineItem, quote, FREE_SHIPPING_MIN

def shipping_banner(items):
    subtotal = quote(items).subtotal
    if subtotal >= FREE_SHIPPING_MIN:
        return "🎉 Your order ships free!"
    remaining = FREE_SHIPPING_MIN - subtotal
    return f"Add ${remaining:.2f} more to get free shipping"
```

This removes the duplicated calculation entirely, so the two modules can't drift out of sync again.

import { randomUUID } from "node:crypto";
import type { Clock, Order, OrderRepository, PaymentGateway } from "./ports";

export interface PlaceOrderCommand {
  /** The client's Idempotency-Key header; every retry of one request reuses it. */
  requestId: string;
  customerId: string;
  amountCents: number;
  currency: string;
}

export class PlaceOrder {
  constructor(
    private readonly orders: OrderRepository,
    private readonly payments: PaymentGateway,
    private readonly clock: Clock,
  ) {}

  async execute(cmd: PlaceOrderCommand): Promise<Order> {
    if (!Number.isInteger(cmd.amountCents) || cmd.amountCents <= 0) {
      throw new RangeError("amountCents must be a positive integer");
    }

    const order = await this.orders.findOrCreate(cmd.customerId, cmd.requestId, {
      id: randomUUID(),
      customerId: cmd.customerId,
      amountCents: cmd.amountCents,
      currency: cmd.currency,
      status: "pending",
      createdAt: this.clock.now(),
    });
    // A retried request gets its original order back: a settled one is returned
    // as-is, and a still-pending one is charged again under the same idempotency
    // key (the order id), so the customer is never charged twice.
    if (order.status !== "pending") {
      return order;
    }

    const result = await this.payments.charge(order.customerId, order.amountCents, order.currency, order.id);
    const settled: Order = { ...order, status: result.ok ? "paid" : "failed" };
    await this.orders.save(settled);
    return settled;
  }
}

The core difference is **checking vs. overriding**.

**`satisfies`** asks the compiler to verify that the expression's inferred type actually conforms to `Record<string, Route>`, while keeping the original inferred (literal) type for later use. When you delete `auth: true`, `{ path: "/settings" }` is checked against `Route`, which requires `auth: boolean` — that's a real structural mismatch, so it's a compile error. This is why `satisfies` catches it.

**`as Route`** is a type assertion, not a check — it tells the compiler "trust me, treat this as `Route`." TypeScript only allows an assertion when the two types are "comparable" in *either* direction (one assignable to the other), not that they're identical or that all required properties are present. Here:

- `{ path: "/settings" }` is **not** assignable to `Route` (missing `auth`) ❌
- but `Route` **is** assignable to `{ path: string }` (Route is a superset — extra properties are fine) ✅

Since one direction holds, the assertion passes the comparability check, even though the object is actually missing `auth`. The compiler doesn't verify the literal has every required field — it just checks the two types aren't *unrelated*.

**Practical consequence:** `legacyRoutes.settings.auth` will type-check as `boolean` but be `undefined` at runtime. That's the classic footgun with `as` — it's an escape hatch that can produce unsound types, whereas `satisfies` gives you compile-time safety *and* keeps type inference narrow (e.g. `routes.home.path` is inferred as the literal `"/"`, not widened to `string`, since `satisfies` doesn't change the expression's type the way an annotation or assertion does).

**Rule of thumb:** use `satisfies` when you want validation against a shape while preserving inference. Use `as` only when you have information the compiler can't derive (and are willing to bypass its checks) — it's not a substitute for validation.
