The difference comes down to what type each construct assigns to the expression, and whether that type is checked against or replaced.

**`satisfies`** checks that the expression is *assignable to* `Record<string, Route>`, but then keeps the original, narrower inferred type for `routes`. It's a validation step, not a type change. So `routes.settings` is still typed as `{ path: string; auth: boolean }` — TypeScript knows precisely which properties exist because it inferred the type from the object literal itself. Since the literal is missing `auth`, it fails the `satisfies` check immediately (object literals get excess/missing property checking against the target type).

**`as Route`** is a type assertion — you're telling the compiler "trust me, treat this expression as a `Route`," overriding its own inference. TypeScript does some sanity checking (the asserted type must overlap with the inferred type), but it does *not* verify that all of `Route`'s required properties are actually present. `{ path: "/settings" } as Route` is really just `{ path: "/settings" }` forcibly relabeled as `Route`, missing property and all. The compiler stops checking structural completeness because you've asserted the type rather than let it be inferred/verified.

So:
- `satisfies` = "verify this literal fits the shape, then let me keep using its precise inferred type." Catches missing/extra properties.
- `as` = "stop checking, just call it this type." Can silently hide missing required fields — which is exactly the bug you found in `legacyRoutes.settings`.

In this case, `legacyRoutes.settings.auth` will be `undefined` at runtime despite TypeScript saying it's `boolean`. That's a real unsoundness hole, not just style — worth flagging as a bug if this pattern shows up elsewhere in the router config.

The difference is that `satisfies` type-checks the expression, while `as` overrides the type checker.

**`satisfies`** validates the object against `Route` *before* inferring its type. Since `Route` requires `auth: boolean`, omitting it is a real type error — same as if you'd written `const x: Route = { path: "/settings" }`. It just also happens to preserve the narrower literal type (`{ path: "/", auth: false }` instead of widening everything to `Route`), which is why you still get autocomplete on `routes.home.path` as `"/"` rather than `string`.

**`as Route`** is a type assertion — it doesn't ask "does this satisfy `Route`," it asks "is `{ path: string }` comparable to `Route`" (i.e., is one assignable to the other in *either* direction). Since `Route` (which has `path` and `auth`) is assignable to `{ path: string }` (drop the extra field, that's fine structurally), the assertion is allowed — even though the reverse assignment (which is what actually matters at runtime) is not valid. `as` doesn't check for missing required properties the way a normal assignment or `satisfies` does; it just checks rough structural overlap and then trusts you.

The practical consequence: `legacyRoutes.settings.auth` is typed as `boolean`, but at runtime it's `undefined`. That's a real unsoundness hole — `as` let you lie to the compiler. `satisfies` can't produce that hole because it never skips the check; it just avoids widening the resulting type.

Rule of thumb: reach for `satisfies` when you want validation *and* to keep the precise inferred type. Reach for `as` only when you know something the compiler can't (e.g., narrowing `unknown` from a JSON parse) — not as a way to silence a "missing property" error.
