## Findings

### 🟡 Warning

**Knowledge Duplication — provider dispatch logic copy-pasted across two scripts**
Symptom: `EXAMPLEGW_BASE_URL`, the `DEFAULT_MODELS` map, the `provider` validation block, and the `thinking: {type: "disabled"}` conditional spread are byte-for-byte identical in `scripts/ci-review.mjs` and `scripts/run-evals-live.mjs`.
Source: Hunt & Thomas — *The Pragmatic Programmer*, DRY / Fowler — *Refactoring*, Duplicate Code
Consequence: the two copies will drift the first time either needs a fix (e.g. gateway URL change, a new provider, or a correction to the thinking-disable behavior) — this PR is itself evidence of the pattern, since it introduced the duplicate rather than a shared helper.
Remedy: extract a small shared module (e.g. `scripts/lib/provider.mjs`) exporting something like `resolveProvider(providerName, requestedModel) -> { model, client, requestOverrides }`, imported by both scripts.

**Knowledge Duplication — "default Anthropic model" decision encoded in three unsynchronized places**
Symptom: `action.yml`'s `model` input default, `ci-review.mjs`'s `DEFAULT_MODELS.anthropic`, and the bash literal `if [ "$MODEL" = "claude-sonnet-4-6" ]` in `action.yml` all separately encode "the default model is claude-sonnet-4-6."
Source: Winters et al. — *Software Engineering at Google*, Ch. 1 (implicit contracts via observable coupling)
Consequence: bumping the default model in one place silently breaks the ExampleGW remap — the gateway then receives a bare, unresolvable model id and fails per-call with a gateway-side error rather than an obvious config error.
Remedy: have the bash remap consult the same table `ci-review.mjs` owns (or move the remap decision entirely into `ci-review.mjs`, since it's already the source of truth for `DEFAULT_MODELS`) instead of re-deriving it as a shell string comparison.

**Coverage Illusion — new provider-branching logic has no test coverage**
Symptom: the diff adds several new decision points (unknown-provider exit, missing-`examplegw-api-key` exit, model remap, thinking-disable branch) with no accompanying test changes.
Source: Feathers — *Working Effectively with Legacy Code*, Ch. 1
Consequence: this logic runs unattended in CI gating merges — a regression here surfaces as a confusing pipeline failure on someone else's unrelated PR, not as a caught test failure.
Remedy: add scenario coverage (via `run-evals-live.mjs`'s own harness or a lightweight script test) for: valid `examplegw` config, missing `examplegw-api-key`, and an unknown `--provider` value.

## Beyond Brooks-Lint: correctness risks worth resolving before merge

These aren't decay/maintainability findings, but they'd block me from approving as-is:

1. **`https://api.examplegw.example` uses a reserved, non-routable TLD.** `.example` is carved out by RFC 2606 specifically so it never resolves on the public internet — if that's literally the string in the source (not a stand-in you substituted for pasting this diff to me), every ExampleGW request will fail DNS resolution. Worth a final grep before merge to confirm it's the real hostname.
2. **Unverified auth header.** The code authenticates to ExampleGW by setting `ANTHROPIC_API_KEY` and constructing a bare `new Anthropic({ baseURL })`. The Anthropic SDK sends that credential via the `x-api-key` header, not `Authorization: Bearer`. Given ExampleGW issues differently-prefixed keys (`sk-gw-...`), confirm it actually reads `x-api-key` — a mismatch fails as a runtime auth error, not at review time.
3. **Disabling thinking to fit the fixed `max_tokens: 4096` budget is a known footgun, not a safe workaround.** On current Claude models, `thinking: {type: "disabled"}` can cause the model to write a tool call or reasoning tags directly into visible text instead of a structured block, with no error raised — which would flow straight into this action's SARIF/JSON output. If ExampleGW proxies real Claude models, prefer leaving thinking on and controlling spend via `output_config: {effort: "low"}` (or raising `max_tokens`) instead of disabling it outright.

## Real bug (likely breaks the feature, and is a credential-leak risk)

**`scripts/run-evals-live.mjs` never reads `EXAMPLEGW_API_KEY`.** The added header comment documents:
```
EXAMPLEGW_API_KEY=... node scripts/run-evals-live.mjs --provider examplegw
```
but nothing in the diff sets `process.env.ANTHROPIC_API_KEY = process.env.EXAMPLEGW_API_KEY` (or passes an explicit `apiKey` to the `Anthropic` constructor). The client is built as:
```js
const client = new Anthropic(provider === "examplegw" ? { baseURL: EXAMPLEGW_BASE_URL } : undefined);
```
Since the SDK falls back to `ANTHROPIC_API_KEY` from the environment when no `apiKey` is passed, this means:
- If the dev's shell has no `ANTHROPIC_API_KEY` set, the call just fails auth — annoying but safe.
- If the dev's shell *does* have `ANTHROPIC_API_KEY` set (common for local dev), running with `--provider examplegw` will silently send their **real Anthropic key** to `api.examplegw.example` instead of the intended `EXAMPLEGW_API_KEY`. That's a credential leak to a third-party endpoint, not just a functional bug.

Compare with `.github/actions/brooks-lint/action.yml`, which does this swap correctly at the bash level (`export ANTHROPIC_API_KEY="$EXAMPLEGW_API_KEY"`) before invoking `ci-review.mjs`. `run-evals-live.mjs` has no equivalent wrapper, so it needs the same swap done in-script, e.g.:
```js
const apiKey = provider === "examplegw" ? process.env.EXAMPLEGW_API_KEY : process.env.ANTHROPIC_API_KEY;
const client = new Anthropic(provider === "examplegw" ? { apiKey, baseURL: EXAMPLEGW_BASE_URL } : undefined);
```
This should block merge — it's the one path in the PR that's directly user-invoked (not wrapped by the composite action), and it does the wrong thing silently.

## Secondary issues worth a look

- **Model remap is too narrow.** Both the action's bash script and `ci-review.mjs`/`run-evals-live.mjs` only remap the model when it's exactly the literal default `claude-sonnet-4-6`. Any caller who explicitly passes `--model` (or overrides the `model` input) with a bare Anthropic ID when `provider=examplegw` will bypass remapping and hit ExampleGW with an unresolvable model ID — per your own comment, "bare Anthropic model ids are not resolvable through the gateway." Worth either validating/prefixing more generally for `examplegw`, or at minimum failing loudly instead of passing through unmapped IDs.
- **No upfront validation of `$PROVIDER` in the bash script.** `ci-review.mjs`/`run-evals-live.mjs` both explicitly reject unknown providers, but `action.yml`'s bash only branches on `= "examplegw"` vs. else-anthropic. A typo like `provider: ExampleGW` silently falls into the anthropic branch and produces a confusing "anthropic-api-key is required" error instead of "unknown provider."
- **Minor:** `examplegw-api-key` is documented as `sk-gw-...` but nothing checks the prefix — low severity, just noting since it's called out in the description text.

The Sonnet 5 + `thinking: {type: "disabled"}` combination used for the ExampleGW path is valid (Sonnet 5 accepts disabled thinking), so that part is fine as-is.

**Bottom line:** fix the `run-evals-live.mjs` API-key wiring before merging — as written it can silently exfiltrate a real Anthropic key to the gateway endpoint. The model-remap narrowness and provider-typo handling are worth a follow-up but aren't blockers.
