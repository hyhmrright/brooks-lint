# Common benchmark vocabulary and output contract

This contract is identical in A (case-only), B (generic checklist) and C (supplied skill). It defines output meanings and permissions, not an answer key. Source/task contracts control diagnosis; do not infer a rule from a filename. Unless a supplied ledger or configuration explicitly selects another preset, use balanced. Report scoped disposition as defect, protected, or unresolved, with the scope and supporting evidence inside the narrative (inside the finalized draft for health/sweep). A qualified local observation is distinct from a proven deployed defect. A retained scored finding is an assertion of an established local obligation; an unknown obligation stays an unscored investigation item.

Risk-code vocabulary (available equally to every arm): R1 Cognitive Overload—difficulty understanding interacting logic; R2 Change Propagation—one requirement change spreads across components; R3 Knowledge Duplication—multiple independently editable owners of one knowledge/policy; R4 Accidental Complexity—unnecessary mechanisms beyond domain needs; R5 Dependency Disorder—dependency direction violates an established boundary; R6 Domain Model Distortion—representation loses a domain identity or invariant. T1 Test Obscurity—test intent is difficult to understand; T2 Test Brittleness—behavior-preserving implementation changes break checks; T3 Test Duplication—repeated test knowledge needs coordinated changes; T4 Mock Abuse—test doubles obscure or replace the behavior that should be checked; T5 Coverage Illusion—checks fail to protect an established relevant behavior; T6 Architecture Mismatch—test boundaries conflict with the intended system seams.

Severity vocabulary: critical requires demonstrated serious impact/exposure; warning is a demonstrated defect or meaningful protection/change burden; suggestion is a supported limited improvement. A possible future problem or optional style preference alone is not a scored finding. Deductions per finding: balanced critical15/warning5/suggestion1; strict20/8/2; legacy-friendly8/3/1. Standalone mode scores are max(0,100-total deductions), using retained findings only. Do not manually calculate health/sweep composites: use the exposed deterministic finalizer.

Health ledger protocol: strictness resolves to balanced unless explicitly configured otherwise; hasDiff=false for a source snapshot without a supplied diff. pr with hasDiff=false is skipped with a reason. For architecture, debt and test, status=assessed requires an evidence-backed completed assessment, not merely no reported findings. Missing evidence uses status=unassessed plus reason. An unassessed required dimension makes the composite unavailable; its weight is not redistributed. An explicitly supplied adjudicated capped ledger governs its own fixture. One causal finding has one scoring owner across passes; multiple independent mechanisms may be separate findings if each is substantiated. Do not invent tests, ownership, developer pain, coverage or execution receipts.

The collection permits only the exposed scoring tool; proposed runnable witnesses are static predictions unless there is a distinct execution receipt. A scoring receipt proves the supplied ledger's arithmetic and report rendering, not its diagnostic truth and not that a test ran. Health output is exactly finalReport from the last successful finalizer call, with no preface/footer. A sweep JSON object's decoded report field is exactly that finalReport; all narrative must be put into the draft before finalization. If an explanation changes, finalize again before returning the report. For all other modes, provide the requested reasoning and an executable witness or a precise reference to supplied executable assertions with inputs and expected outcomes; an honest 'not run' statement is acceptable.

Sweep artifacts follow the complete schema in each sweep task. No model patch is executed by collection; returned code remains untrusted. Proposed replacements never establish a verified repaired repository. Further sandbox checks, if separately run, report their own receipts and cannot retroactively validate unsupported claims of execution in a model answer.

## Prospective assessment rules

Assess the requested local scope. Cite the supplied files and governing obligation, show a reproducible behavioral or change witness, and state what was not executed. A complete local inventory can support its local test assessment even when architecture or maintenance history is unknown. A label is not a complete task outcome. For health and sweep, reconcile each scored prose finding with one ledger owner before finalizing and deliver the entire finalReport unchanged. No candidate code can be executed during collection; later sandbox checks have separate receipts.
